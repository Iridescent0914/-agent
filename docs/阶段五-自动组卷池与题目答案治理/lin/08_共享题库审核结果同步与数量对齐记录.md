## 问题与定位

E013使76变为77；另两题的题型变更影响选择/填空筛选数量。此前治理文档已指出E013为数据库与来源基线的差异，但没有供其他环境应用的共享审核数据。此次只传递既有审核决定，不重新推断题目答案；E013原始资料矛盾的`pool_source_conflict`证据保留，不宣称本轮已解决数学资料冲突。

用户只提供协作者73这个数量，未提供其数据库逐题清单，不能据此断言具体缺失哪四组。新同步预览会在协作者机器列出真实差异，覆盖已纳入仓库的来源修复与本次共享审核。

## 实现

- 新增`data/config/question_catalog_reviews.json`：按稳定`original_qid`保存四题明确的before/after字段及题干、选项、原参考的SHA-256来源校验，不复制数据库UUID、教师身份或学生数据。
- 新增`question_catalog_sync`服务及`scripts.sync_question_catalog`命令。同步范围为原始目录79组选择/填空/判断题，应用共享审核后77组就绪、2组解答题非就绪。其余101组来源题及任何额外导入题不写入。
- 对仅有系统归一化/治理历史的题应用仓库修复；对人工审核题只接受已经一致或共享配置明确记录的旧状态。其他人工答案、不同题干、归档和缺题形成冲突，整批拒绝。资源relationship元数据的差别按实际路径比较，避免仅序列化格式不同就误判冲突或覆盖资源。
- 写入前备份待变更题的原内容、审核历史、修订及时间到被Git忽略的`data/uploads/question_catalog_sync/`；随后锁题、追加`question_catalog_synced`事件并更新内容指纹。默认仅预览；无`--apply`不生成备份或写库。
- 同一事务前后比较8张业务保护表的数量与内容摘要：试卷、题项快照、提交、作答、作答修订、掌握度、素养分和知识点状态。同步不修改这些表，也不自动重新评分。
- 修复种子导入的回退风险：旧逻辑只保护答案，仍会用来源题型覆盖人工编辑的题型。现在对`content_updated`或`question_catalog_synced`记录一并保护已编辑内容、题型和标签。新共享变更通过显式同步命令审核应用。

原始来源文件及`question_pool_corrections.json`保持原样，可继续追溯源Word和早期治理记录；共享配置单独承接数据库审核状态，避免重建来源时把业务审核伪装成原资料结论。

## 协作者操作

```powershell
git pull --ff-only
docker compose exec backend python -m scripts.sync_question_catalog
docker compose exec backend python -m scripts.sync_question_catalog --apply
docker compose exec backend python -m scripts.sync_question_catalog
```

第一步预览若有冲突，先处理对应题目，不覆盖人工审核。已存在180组题库时无需为了数量同步重新初始化数据库。只有报告缺题时，先运行`seed_database --chapter all`，再预览同步。

`target_pool_count=77`表示该79组共享范围的目标，`database_pool_count`表示整库当前数量，`scoped_current_pool_count`表示该范围实际数量。范围外已入池题会列在`outside_scope_ready_ids`，不会为了凑成77而删除或撤回。共同题库以题号、内容和审核状态核对，不能仅比较总数。
