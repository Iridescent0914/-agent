# 阶段四：批量题目入库——阶段开发计划

> 文档状态：S0 开发契约可供 S1 使用；甲方口径与缺失样本后续补验
> 编写日期：2026-11-05；按当前仓库与 DeepSeek 官方接口于 2026-11-09 校订  
> 关联文档：[开发计划.md](./开发计划.md)  
> 本文用于安排开发顺序和阶段验收，不包含业务代码修改。

## 一、阶段划分总览

本功能拆分为 7 个开发阶段。各阶段形成可检查的交付物；已明确的契约可支持后续内部开发。缺失样本和甲方未确认口径单独跟踪，在涉及真实模型调用或对外试用前完成相应验收，不把尚无样本的场景伪称已通过。

| 阶段 | 名称 | 核心结果 | 是否可供教师正式使用 |
| --- | --- | --- | --- |
| S0 | 需求与数据契约冻结 | 标签白名单、状态与模型协议、评测方案确定 | 否 |
| S1 | 导入基础设施与暂存区 | 批次、候选题、文件存储和可恢复任务链路可用 | 否 |
| S2 | PDF/DOCX 解析与规则切题 | 不依赖模型也能提取文档内容并生成初步候选题 | 否 |
| S3 | 模型提取、答案处理与精准标签 | 结构化题目、生成或配对答案、预审题答，标签限于正式目录 | 仅内部测试 |
| S4 | 重复题检测 | 索引查询批内和题库内的精确/疑似重复题 | 仅内部测试 |
| S5 | 教师审核工作台 | 教师核对题目、标签和答案，最后处理待认领内容 | 试运行 |
| S6 | 正式入库与验收 | 事务性建题，按教师选择和现有答案校验决定是否入池 | 满足身份和模型评测门槛后试用 |

总体依赖关系：

```text
S0 契约冻结
  ↓
S1 暂存与任务基础
  ↓
S2 文档解析
  ↓
S3 模型提取与标签
  ↓
S4 重复检测
  ↓
S5 教师审核工作台
  ↓
S6 正式入库与验收
```

S2、S3、S4 可以在接口契约稳定后部分并行开发，但合并验收仍按上述顺序进行。

## 二、S0：需求与数据契约冻结

> 2026-11-10 更新：已形成[需求与状态契约](./S0/需求与状态契约.md)、[候选题 JSON Schema](./S0/候选题.schema.json)、[全量标签目录](../../../data/knowledge_graph_catalog.json)及[评测标注说明](./S0/评测标注与验收.md)。评测输入改用 `校本/题` 下的 PDF；可在导入工作台一次确认题目和答案并直接入池。前两章 KP—节映射已写入种子树及数据库修复迁移，详见[修复记录](./KP主属节映射修复记录.md)。现有契约可供 S1 内部开发；题级人工基线、部分甲方口径和缺失场景仍须按使用阶段补验。

### 1. 阶段目标

把容易产生返工的业务口径先确定下来，形成前后端、模型和数据库共同遵循的契约。

### 2. 开发内容

- 盘点正式知识点数据，确认首批开放的年级、章、主属节和 KP 范围。
- 冻结当前题型枚举 `choice / fill_blank / calculation / solution / true_false`、1—5 星难度参照、八项核心素养及“必做”的业务含义；候选可暂存 `unknown`，正式题不可写入。
- 明确标签依赖关系：HTML 是知识图谱编辑来源，运行时读取由它导出的 `data/knowledge_graph_catalog.json`。主属 KP 驱动章、节和年级；只有目录中带正式 KP code 且数据库存在的知识点才可入库。后续章节正式开放前须先分配并导入稳定 code，不能从名称或 code 猜节。
- 定义候选题 JSON Schema，包括题干、选项、答案、解析、图片、标签、证据位置和字段置信度。
- 冻结三种文件场景：只有题目、题目与答案同文件、题目与答案分文件；答案来源区分资料提取、模型生成、教师录入和缺失。
- 明确两项审核门槛及一次操作路径：导入工作台可同时确认题目内容、标签和结构化答案，后端同事务建题并复用现有答案晋级服务，分别留审核事件；仅确认题目者为 `raw_answer_only`，以后再审答案。
- 定义题答匹配、模型预审、教师确认及待认领答案/图片/疑似漏题的状态与审计字段。
- 定义批次状态、候选题标签状态、教师决定状态和错误码。
- 定义 PDF、DOCX、文件大小、页数和单批题量限制。
- 确认原文件是否允许发送给 DeepSeek，以及文件保留期限和去身份化要求；不能用含学生个人信息的真实资料先跑模型再补确认。
- 核对 DeepSeek 账号可用的文本/图片模型；Chat JSON 模式只保证合法 JSON，应用端仍需严格 schema 校验，PDF/DOCX 由本地解析或转图片后发送。
- 明确演示与多教师试用边界：当前只有 `operator_name` 字符串，正式多教师试用前须有可信服务端身份与批次归属校验。
- 开发和试解析时直接使用现有 PDF。需要客观计算切题、答案匹配和标签准确率时，再对测试中遇到的部分题目保留人工核对结果（来源位置、题干、答案证据、KP、重复关系）；这不是上传前或 S1 开发前必须完成的步骤，不设固定 100 题门槛。
- 当前已有文本层 PDF、无答案与分文件题答资料。扫描页、题答同文件、明确错位答案等目前没有经确认样本，列为后续补测；在拿到真实样本前可用受控合成资料验证处理逻辑，但不得宣称已验证真实资料的识别效果。

### 3. 阶段交付物

- 《批量导入业务口径说明》；
- 候选题 JSON Schema；
- 状态机和错误码文档；
- 正式标签枚举及知识点范围清单；
- 页级样本索引、题级标注规则和逐步扩充的人工复核样本；
- DeepSeek 模型、服务端配置、批次预算和失败处理方案；
- 章—年级映射及多教师试用的身份方案。

### 4. 验收标准

- 同一题目在产品、后端和模型侧使用相同字段定义。
- 模型无法确定 KP 时允许返回 `needs_confirmation` 或 `out_of_scope`，不存在“必须猜一个标签”的要求。
- 章、节、KP、核心素养之间的冲突处理规则明确。
- 模型生成答案与资料原答案分开存储；模型预审只提示疑点，不能代替教师确认。
- 已标注样本可回溯原文件，疑难项经过人工复核；未覆盖场景与后续补测时点明确记录。
- 甲方尚未确认的事项被显式列为未决项，不以代码中的临时值代替业务决定。

## 三、S1：导入基础设施与暂存区

### 1. 阶段目标

先建立“原文件—导入批次—候选题—正式题目”之间的持久化中间层，使后续解析和模型调用可恢复、可重试、可审计。

### 2. 后端开发

- 新增 `question_import_batches` 导入批次表。
- 新增 `question_import_items` 候选题表。
- 给正式题目增加规范化指纹和来源批次/来源项字段；旧题可能已有重复，暂不对全表指纹加唯一约束。
- 增加 Alembic 迁移，并为历史题目回填规范化指纹；只报告历史重复，不自动删除。
- 建立私有文件存储目录或对象存储封装：
  - 服务端重命名；
  - 校验真实 MIME 和文件头；
  - 计算 SHA-256；
  - 拒绝加密文件、宏文档和异常压缩文件。
- 实现批次创建、查询、取消、候选题查询和修改接口。
- 候选题修改使用 `revision` 乐观锁。
- 建立基于数据库状态的有界任务 worker，支持任务领取、心跳、检查点、超时重领和单块重试。
- 实现确定性的 fake 模型适配器，仅供自动化测试和界面联调。

### 3. 前端开发

- 建立批量导入任务列表和基础路由。
- 完成文件选择、格式/大小提示和上传进度。
- 显示批次状态、当前步骤、失败信息和重试入口。
- 此阶段不对教师正式开放批量入库。

### 4. 阶段交付物

- 数据库迁移文件；
- 批次和候选题基础 API；
- 私有文件存储服务；
- 数据库任务 worker；
- fake provider；
- 批次列表及上传页面骨架；
- 对应单元测试和接口测试。

### 5. 验收标准

- 同一文件和配置重复上传时能识别已有批次，不重复创建模型任务。
- 页面刷新或服务重启后仍能查询批次和已保存候选题。
- 两人同时修改同一候选题时，后提交者收到版本冲突而不是覆盖前者。
- fake provider 结果被明确标记，不能作为正式题目提交。
- 文件不能通过公开、可猜测的静态 URL 访问。

## 四、S2：PDF/DOCX 解析与规则切题

### 1. 阶段目标

优先用确定性工具完成文档内容提取和常规题目切分，减少模型调用量，并为模型提供带来源位置的高质量输入。

### 2. 开发内容

- PDF 使用 PyMuPDF 提取：
  - 每页文本和文本块坐标；
  - 页面图片；
  - 必要时的页面渲染图。
- DOCX 使用 `python-docx` 提取：
  - 段落和编号；
  - 表格；
  - 内嵌图片及其相邻文本关系。
- 对 DOCX 公式与编号补读 OOXML/OMML；无法可靠还原的数学对象保留原文证据并进入教师核对，不能只依赖 `paragraph.text`。
- 实现文本预处理：Unicode、全半角、空白、页眉页脚、跨页连接等。
- 实现常见题号、选项、子问题、答案和解析标记识别。
- 三种文件场景分别提取题目与答案；分文件时先按题号、小题号和资料结构配对，顺序只能作为待确认线索，不静默确认为答案。
- 保存原始文本和清洗后文本，不覆盖原始证据。
- 图片单独存储并计算内容哈希，不在业务 JSON 中保存大段 Base64。
- 过滤封面、目录、版权信息；孤立图片、未配答案段和疑似漏题保留原位置，进入批次末尾“待认领内容”。
- 对无法可靠切分的文本块标记 `needs_model_split`，不强行生成题目。

### 3. 阶段交付物

- PDF 解析服务；
- DOCX 解析服务；
- 文本预处理和规则切题模块；
- 题目/答案初步匹配模块；
- 题目图片资产处理模块；
- 解析样本和快照测试。

### 4. 验收标准

- 文本型 PDF 和常规 DOCX 可以生成带来源页码/段落位置的候选题。
- 扫描页会进入待视觉模型处理状态，不产生空白题或乱码题。
- 未被任何题目认领的图片不会被自动包装成普通题目。
- 匹配不到题目的答案和图片能在批次末尾查看、指定归属、排除或保留待处理，不影响已确认题目先行处理。
- 规则切题无法确定时保留原始区块并等待模型处理，不静默丢失内容。
- 任一候选题可以定位回原文件中的页码或段落。

## 五、S3：模型提取、答案处理与精准标签

### 1. 阶段目标

接入真实模型完成复杂切题、题目结构化、答案生成/配对/预审和标签建议，同时从技术上阻止模型生成游离于本系统之外的正式标签。

### 2. 开发内容

- 建立真实模型 provider，API Key 仅保存在服务端环境变量中。
- 实现超时、限流、重试、熔断和模型调用日志摘要。
- 文本提取优先；扫描页、公式图片或复杂布局由本地渲染/裁剪成图片，再调用支持图片输入的 DeepSeek 模型。该能力只用于题目导入，不改变 M6 学生答题识别状态。
- 每次分类时从数据库读取当前导入范围内的正式 KP 候选快照。
- 模型只能返回正式候选 code 或未确定，不能自由生成知识点字符串；候选需包含名称、章、节和辨析说明，防止同名或近义 KP 误选。
- Chat Completions 使用 `json_object`；后端独立执行严格 JSON Schema/Pydantic、白名单和目录快照复验，拒绝空响应、截断和未知 code。
- 模型返回未知 code、非法题型、非法核心素养时拒绝该字段并产生校验问题。
- 根据最终 KP 派生章、主属节，按已核准映射校验年级；八项核心素养还须与 KP 允许集合核对，例外由教师留理由。
- 为关键字段保存置信度、备选 KP 和原文证据。
- 支持按单题重新提取、重新分类，不强制重跑整个批次。
- 只有题目时，由教师对全部或选中候选题触发答案生成，也可直接手填；生成答案标注来源、版本和待教师确认状态。
- 题答同文件或分文件时，模型对配对给出候选与原文依据；独立预审调用检查题号、选项、数值和题意是否明显冲突，输出“匹配/疑似错配/无法判断”及证据，不自动确认答案。
- 生成答案、资料答案和教师手填答案分别留痕，不能互相覆盖来源；明显冲突要突出展示给教师。
- 保存 provider、model、prompt_version、schema_version 和响应摘要。
- 将上传文档视为不可信数据，防止文档内提示词改变系统任务。

### 3. 阶段交付物

- 真实模型适配器；
- 切题、结构化、标签分类、答案生成、题答配对和独立预审提示词及版本记录；
- 严格响应校验器；
- 标签白名单和关联字段派生服务；
- 单题重试接口；
- 模型效果评测报告。

### 4. 验收标准

- 100% 的正式 KP 建议来自数据库候选白名单。
- 当前知识图谱未覆盖的题目能进入 `out_of_scope`，不会被强行归类。
- 模型无效 JSON、超时或非法标签不会导致整个批次结果丢失。
- 资料答案忠实提取；模型生成答案独立标记且须教师确认；预审异常能定位原题、原答案和疑点。
- 能统计切题正确率、字段完整率、KP Top-1/Top-3 准确率和教师预估修改率。
- 真实模型与 fake provider 在界面和数据中可以明确区分；fake 批次不能正式入库。

## 六、S4：重复题检测

### 1. 阶段目标

在教师审核前尽量找出重复题，并在正式提交时提供并发条件下的最终保护。

### 2. 开发内容

- 实现题目规范化纯函数，保留数字、正负号、单位、比较符号和选项顺序。
- 计算题干、选项和关键图片共同构成的规范化 SHA-256。
- 检测同一批次内的精确重复题。
- 历史题指纹一次回填、后续建题或编辑时维护；批量用 B-tree 索引按指纹查询题库精确重复，不逐题遍历全库。
- 使用 PostgreSQL `pg_trgm` 索引召回少量文本疑似重复题，再做 Top-K 精排与并排差异展示；中文题干召回效果需实测。
- 同年级、章节、KP 和题型优先比较，但不以标签不同为理由跳过查重。
- 对图片题增加图片内容哈希和感知哈希；关键图不同不能仅凭文字相同判为精确重复。
- 对题干高度相似但答案不同的情况增加“疑似数据冲突”提示。
- 精确重复默认“跳过并关联已有题”；新文件若带来更完整答案或图片，形成已有题补充建议，由教师在现有编辑/审核流程处理，不自动覆盖；疑似变式允许教师确认独立入库并记理由。
- 用标注过的重复题与合法变式题评测后冻结相似度分级和阈值；计划中的示意数值不直接上线：
  - 精确重复：禁止作为新题导入；
  - 高疑似：默认阻止，需填写强制导入理由；
  - 中疑似：警告并由教师确认；
  - 低相似：不主动打扰教师。
- 在候选题生成后、教师修改后和正式提交事务内分别执行重复检查。

### 3. 阶段交付物

- 规范化和指纹模块；
- 历史题目指纹回填报告；
- 精确重复检测服务；
- `pg_trgm` 疑似重复召回服务；
- 图片相似度服务；
- 重复检测接口和评测报告。

### 4. 验收标准

- 相同题目改变题号、空格、全半角或选项标号后仍能识别。
- 数字、符号、单位或选项发生实质变化的题目不会被当作精确重复。
- 批内精确重复和题库精确重复默认无法作为新题提交。
- 疑似重复结果能够返回已有题 ID、相似度和主要差异，供前端并排展示。
- 两个批次并发提交同一精确重复题时，不会同时产生两道正式题。
- 真实题库查询使用指纹和相似度索引，记录批量查重耗时；原题答案和图片不会因重复导入被静默改写。

## 七、S5：教师审核工作台

### 1. 阶段目标

提供教师真正可用的导入审核界面，在同一候选题卡片核对题目、标签、答案来源和判分方式，再集中处理待认领内容和重复题；教师可一次确认两项审核。

### 2. 开发内容

- 完成五步式工作台：
  1. 选择三种文件方式、答案生成/预审选项与标签范围；
  2. 查看解析进度；
  3. 复核和修改题目、标签、资料答案/生成答案/手填答案；
  4. 集中处理重复题、错配答案及待认领图片和疑似漏题；
  5. 查看提交前检查和结果。
- 左侧显示候选题列表，右侧并排显示原文证据和结构化编辑区。
- 表格展示题号、题干摘要、题型、难度、年级、章、节、主属 KP、核心素养、必做、标签状态和重复状态。
- 支持按低置信、超范围、缺答案、生成答案未确认、预审疑似错配、精确重复、疑似重复等状态筛选。
- 支持合理的批量修改，但批量修改后重新执行一致性和重复检查。
- 主属 KP 使用正式知识点选择器；改选后自动刷新章、节等派生字段。
- 支持题干、选项、答案、解析和图片的数学内容预览与编辑。
- 重复题页面并排展示候选题和已有题，并突出差异。
- 明确区分“保存修改”“确认题目与答案并入池”“仅确认题目并入库”几个动作；支持教师审阅后批量执行，并在提交前展示两条路径的题目数量。仅入库题显示“答案待审核”及现有答案审核入口。
- 展示版本冲突、模型失败、标签越界和文件解析警告。

### 3. 阶段交付物

- 批量导入完整工作台；
- 原文证据预览和题目编辑组件；
- 正式标签选择与联动组件；
- 重复题并排比较页面；
- 待认领内容集中处理页与答案来源、预审疑点展示；
- 教师决定和批量操作能力；
- 前端组件测试和端到端测试。

### 4. 验收标准

- 教师可以独立完成三种文件方式、查看模型结果、修改标签与答案、拒绝无效题、处理重复题和待认领内容。
- 页面刷新、网络中断或重新登录后，已保存审核结果不丢失。
- 教师不能输入不存在的正式 KP，也不能制造章、节和 KP 冲突。
- 低置信、范围外和重复题有明确文字提示，不能只依赖颜色。
- 只有已标记 `approved` 且无阻断问题的候选题可以进入待提交集合。
- 教师可在批量工作台一次确认题目和答案；后端仍分别执行题目审核与现有答案晋级校验。未解决的答案/图片可保留待处理，不会被错误挂到题目上。

## 八、S6：正式入库与验收

### 1. 阶段目标

完成事务性正式入库，并衔接现有答案审核与组卷池规则，通过甲方试运行完成交付。

### 2. 后端开发

- 建立批量建题领域服务，统一字段校验、资产关联、答案来源和审计。
- 提交时检查候选题 `revision`、教师决定、标签一致性和重复状态。
- 在同一数据库事务中完成最终查重、正式建题、候选题回写和审计记录。
- 使用事务锁或 advisory lock 防止并发重复入库。
- 提交接口要求幂等键；相同请求重试只能返回首次结果。
- 教师在导入页确认题干、图片和标签后建题，`source_review_status=reviewed`；若同时确认结构化答案且通过现有答案晋级校验，事务中直接设为 `machine_ready`，分别留下题目和答案审核事件。否则仅入题库并保持 `raw_answer_only`；模型生成或预审不能替教师确认。
- 原文件题号保存在候选项；正式 `source_question_number` 使用整数批内序号，并生成独立命名空间 `original_qid`。
- 写入来源文件、批次、原题号、模型版本和教师修改摘要。
- 题目、答案来源、教师确认、入池检查结果和重复处理选择分别留审计记录。

### 3. 前端开发

- “批量导入”提供三种文件方式及答案生成、手填、预审和末尾待认领处理入口。
- 在正式题库列表中展示批次来源，并可回看导入审计摘要。
- 保留已有题目的查看、编辑、答案审核和状态晋级功能。

### 4. 全链路测试

- 现有真实 PDF 用于无答案和分文件题答的全链路测试；PDF、DOCX、扫描页、题答同文件及明确错位答案等处理分支可先用受控固定样本验证。缺失的真实场景取得资料后补测，在此之前不得宣称其真实资料识别效果已验收。
- 模型超时、非法 JSON、低置信标签和知识图谱范围外题目。
- 批内重复、题库重复、相似变式和答案冲突。
- 同批重复提交、多人并发编辑、两批并发导入同题。
- 提交中任一题失败时整组事务回滚。
- 服务重启后任务恢复和人工重试。
- 同页同时确认且通过现有答案晋级校验的题直接入池；仅入库题保持 `raw_answer_only`。两项审核事件独立可追溯，校验失败不得静默降级。
- 未认领答案、图片和疑似漏题在批次末尾可处理或保留；已确认题目可先行提交。
- fake 适配器只能用于联调；入库事务用受控真实模型响应桩测试，DeepSeek 的提取、生成与预审效果用标注样本单独验收。

### 5. 甲方试运行

- 选取首批开放章节的真实资料进行试导入。
- 记录每批处理耗时、模型成本、切题错误、标签修改率、重复误报/漏报。
- 由甲方教师完成盲测和问题确认。
- 只修复影响数据正确性和主流程的问题，新增范围需求进入后续版本。
- 形成试运行报告、已知限制和操作说明。

### 6. 阶段交付物

- 事务性批量入库服务；
- 答案来源、题答预审、待认领内容与入池状态的验收记录；
- 完整自动化测试报告；
- 人工标注集评测报告；
- 甲方试运行记录；
- 部署、配置、备份恢复、文件清理和教师操作文档。

### 7. 最终验收标准

- 三种文件方式均可从上传走到教师确认和正式建题；无答案题可选模型生成或教师手填。
- 已有题目的编辑、审核和历史作业快照不受批量导入影响。
- 所有正式入库题均经过教师 `approved`，并可追溯原文件、模型版本和教师修改。
- 所有正式 KP 均来自数据库白名单，未知 code 100% 被拒绝。
- 精确重复题不能作为新题入库；高疑似题必须经过明确决策。
- 提交具有幂等性和事务性，失败不会产生半批数据。
- 未经教师明确确认结构化答案和现有答案晋级校验的题 0% 进入 `machine_ready`；合格题可在导入事务中直接入池，两个审核事件均可追溯；仅入库题保持 `raw_answer_only`。
- 题答预审异常与未认领答案/图片可集中处理，未处理项不丢失，也不会被误标为已确认。
- fake provider 不能用于正式入库；DeepSeek 图片输入、JSON 输出、失败重试和本地 PDF/DOCX 解析均经过真实样本验收。
- 多教师真实资料试用前，服务端身份、批次归属和授权校验已经落地；否则只允许隔离内部演示。
- 评测报告至少包含切题正确率、字段完整率、KP Top-1/Top-3 准确率、重复召回率、重复误报率、教师修改率、处理耗时和模型成本。

## 九、开发提交与评审建议

每个阶段建议拆成小型、可回滚的提交，不把数据库迁移、解析器、模型提示词和大规模前端页面混在一个提交中。每阶段结束执行一次评审：

1. 数据库和 API 契约评审；
2. 安全和隐私检查；
3. 自动化测试；
4. 使用固定评测集回归；
5. 更新阶段文档和已知问题；
6. 确认无阻断问题后进入下一阶段。

建议在 S3、S5、S6 设置三个明确里程碑：

- **内部模型里程碑**：模型能从正式白名单贴标，但暂不允许正式入库；
- **教师试用里程碑**：教师能在同一工作台完成题目、标签和答案确认，并处理或保留待认领内容；
- **正式交付里程碑**：事务性入库、重复保护、真实模型评测和身份边界全部完成。

## 十、阶段完成定义

任一阶段只有同时满足以下条件才算完成：

- 本阶段交付物已进入版本库；
- 数据库迁移可以正向执行，并有明确回滚或恢复方案；
- 新增核心逻辑有自动化测试；
- 对固定评测样本执行过回归，结果已记录；
- 不把 fake、硬编码或手工数据库操作当作正式实现；
- 已知问题有严重级别、影响范围和后续安排；
- 相关文档与实际行为一致；
- 阶段验收人确认通过。

若某阶段验收失败，应优先修复该阶段的阻断问题，不带着数据一致性、标签越界、重复写入或安全问题进入下一阶段。
